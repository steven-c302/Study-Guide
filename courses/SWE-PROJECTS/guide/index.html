The MERN Stack

MERN = MongoDB, Express, React, Node.js — four pieces that together let you write a full web app (frontend + backend + database) in one language, JavaScript.

MongoDB — the database

A NoSQL document database. Records are stored as JSON-like documents instead of rows in fixed tables, so two documents in the same collection can have different fields. Good fit when data is naturally variable-shaped — e.g. recipes with different numbers of ingredients, optional sections, nested steps and comments (this is why Larder's community-cookbook feature uses Mongo).

Not a good fit for data with strict relationships that need to stay consistent (users, orders, foreign keys) — that's what a relational database (Postgres) is for.

Express — the backend framework

A lightweight framework that runs on top of Node.js and handles HTTP routing and middleware. You define routes (app.post('/api/recipes', handler)) and Express wires up request parsing, responses, error handling, etc. It's the "plumbing" layer between your React frontend and your database.

React — the frontend library

Builds UI out of reusable, stateful components. Instead of manually updating the DOM, you describe what the UI should look like for a given state, and React re-renders efficiently when that state changes.

Node.js — the runtime

Lets JavaScript run outside the browser, on a server. Express (and Next.js) are both built on top of Node — it's the foundation, not something you "add" separately once you're using either framework.

Your actual stack vs. full MERN

Larder (the pantry-tracker project) uses Next.js + PostgreSQL/pgvector + MongoDB, not plain MERN. Short version: keep it that way — you'd be trading down on two fronts to "match" MERN exactly.

AI Engineering Concepts (for Larder + interviews)

Structured output / schema-constrained generation

Instead of asking an LLM for free text and hoping it's parseable, you give it a JSON schema (or use function-calling) and it returns data in that exact shape. This is the first AI skill Larder's recipe-scan feature is built around — more reliable than prompting for "nice formatting" and asking your code to guess at parsing it.

Vision / multimodal prompting

Sending an image (a recipe card, a fridge photo) to a multimodal LLM alongside a text prompt, and combining it with structured output to get clean data back (ingredients, quantities, detected items).

Embeddings

A way of converting text (a recipe, a query) into a vector of numbers such that similar meanings end up close together in that vector space. This is what makes "find recipes similar to what I have" possible without exact keyword matching.

Vector search / pgvector

Once everything is embedded, you can search by similarity (cosine distance) instead of exact match. pgvector adds this capability directly inside PostgreSQL, so you don't need a separate vector database for a project this size.

RAG (Retrieval-Augmented Generation)

The pattern behind Larder's recipe recommendations: retrieve relevant candidates first (via vector similarity search over your recipe corpus), then generate — have the LLM adapt/rank/explain those real, retrieved recipes rather than hallucinating one from scratch. This is meaningfully more than "call an API and print the answer," and it's the concept to lead with when asked about AI work.

Tool-calling / agentic workflows

Letting an LLM call your own functions (e.g. "search pantry," "search recipes") instead of guessing at data. The model decides which tool to call and with what arguments; your code executes it and returns the result. This is the mechanism behind Larder's planned chat assistant.

Knowing when not to use AI

Expiration-window lookups and grocery-list diffing in Larder are both deterministic (a rules table, a set difference) — no LLM involved. Explicitly choosing not to use AI where it isn't needed is itself a signal worth naming in an interview.

MCP — Model Context Protocol

An open standard (from Anthropic, now broadly adopted) for connecting an LLM to external tools and data sources in a consistent way. Instead of every app hand-rolling its own tool-calling integration, an MCP server exposes a set of tools/resources, and any MCP-compatible client (Claude, other agent frameworks) can connect to it the same way.

Where this fits Larder: the planned chat assistant's tools ("search pantry," "search recipes," "get expiring items") could be exposed as an actual MCP server instead of hand-rolled function-calling — a more current, more legible resume line. Lower priority than the core RAG pipeline — add once that's solid, not before.

Quick glossary

REST API — a convention for structuring web APIs around resources and HTTP verbs (GET/POST/PUT/DELETE).

ORM (e.g. Prisma) — a library that lets you query a relational database using code/objects instead of raw SQL.

SSR (Server-Side Rendering) — generating HTML on the server per-request, instead of shipping a blank page and building it entirely in the browser. One of the things Next.js gives you over a plain React SPA.

PWA (Progressive Web App) — a website that can be installed like an app and access device features (camera, push notifications) via the browser, no app-store review needed.

Cosine similarity — a way of measuring how "close" two vectors point, used to compare embeddings.
